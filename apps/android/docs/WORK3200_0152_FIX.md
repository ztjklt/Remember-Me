# 0.15.2：录音计时、暂停恢复与同步失败修复

针对 2026-10-16 用户实物反馈：计时超过 10 秒停止、暂停恢复状态异常、同步有进度但手机保存 0 段、错误 -1，以及字节/KB 显示难以理解。

## 已确认的原因

1. App 的 `RecorderTimeline.elapsedMs` 把两次回报之间的计时限制为 10 秒。现改为在已知录音状态下用单调时钟持续计时，暂停和断线冻结。结束后以设备文件信息、解码音频时长校准，不把估算当作设备最终时长。
2. 实际 1.3.02 AAR 的 `AudioMessageDispatch.onReceiveAudioStatusChanged` 恢复回调是 `(1, 0, -1)`。原实现拒收无文件编号的恢复事件。现只将它关联到已知的当前录音，空闲或未知会话仍拒绝猜测关联。
3. 实际 AAR 的 `D3200Device.getFilePath` 是 `saveFolder + fileId + ".opus"`，不会补路径分隔符。旧 App 传入无尾部 `/` 的目录，SDK 把文件写成目录旁边的文件，App 随后按目录校验拒绝，产生 `received_file_path/-1`。这是已经在真实 AAR 路径构造器复现的确定性错误，与截图一致；这台手机的完整日志尚未取得，不能据此排除其他实物问题。现三种传参入口（蓝牙、Wi-Fi、实时数据）都规范为带尾部分隔符，保留目录、文件存在和非空校验。
4. App 等待暂停/恢复回执时，实体按钮结束录音会让旧命令阻塞同步。现结束事件撤销已过时的暂停/恢复等待，不改变设备发来的录音状态。

另外，文件错误按文件编号路由，其他文件或实时通道的迟到回调不会直接取消无关下载。收到 100% 或 SDK 处理完成回调仍需文件校验、保存和音频转换，不能单凭回调声称可以试听或已上传。

## 数字从哪里来

- 电量来自 `DeviceInfo.deviceBattery` 和 `onBatteryInfoChanged`。官方范围 0–10，显示百分比为它乘以 10。因此 90% 对应设备档位 9，精度为 10% 一档。
- 固件来自 `DeviceInfo.firmwareVersion`，原样显示。截图中的 `04.92` 不是生产代码常量。
- 传输量来自 `onTransferFileProgress(total, received)`。截图 `279710` 对应显示 `0.280 MB`，`76194` 对应 `0.076 MB`，没有修改底层计数。SDK 传输计数与解密后的裸 Opus 文件大小可以不同。
- 容量来自 SDK 的 `freeMemoryKB`、`totalMemoryKB`，KB 按 1024 字节换算后显示十进制 MB（1 MB = 1,000,000 字节）。未知值显示“未知”，不补默认电量、固件或容量。
- 测试代码有明确标注的模拟设备事件；它们属于独立测试 APK，不在生产 App 中启用。演示截图不可当作实物成功证据。

## 更新后怎样验收

保持已有 App 数据，使用同一签名的 0.15.2 覆盖安装，不需要开启 USB 调试。打开勿忘我并连接录音豆：

1. 可先展开“设备录音与连接管理”，刷新并下载之前失败的录音。原设备文件未被本次修复删除。
2. 新录约 40 秒，观察数字越过 10 秒继续计时。试一次 App 暂停、恢复，再用实体按钮结束。
3. 观察“接收数据 → 本机校验 → 音频转换 → 已保存”，手机保存数量增加后试听，核对声音和时长。
4. 本人确认上传后才进入转写、文字核对和重点整理。本版没有自动上传用户音频。

若还有失败，在连接管理底部“导出连接与下载记录”。本版记录设备原始信息、状态/文件编号/时长、传输错误阶段、文件是否在目标目录、实际文件大小、校验和解码结果；不会导出授权 token 或厂商业务密钥。

本次修改范围是 Android SDK 适配与显示，未修改后端/AI 合同。代码验证不能替代 vivo 与实物的无线通信、实际录音格式和清晰试听验收。
