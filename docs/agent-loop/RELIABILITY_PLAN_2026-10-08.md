## 执行任务与兼容性提案

1. 音频能力探针：已完成，云端转写被上述外部条件阻塞；现有真实处理材料继续用于后端验证。
2. 问答证据：内部请求按原文、记忆解释分别组织，仅去除同一个证据 ID 的重复包装；不同来源即使原文相同仍分别保留。时间上下文与已确认归纳的来源对应关系保留。使用短引用编号，返回前映射实际证据 ID；共享 Twin 输出语义不变。新真实问答批次独立保存，不覆盖既往失败。
3. 人物更新：在既有 ProfileCandidate 上追加 ProfileUpdate 审核历史和接口，不另建事实库。用户选择候选与目标并明确确认动作；本轮不宣称模型自动识别完备的四类关系。
4. 网页、Android：展示更新建议、支持/反例、目标和模糊时间；确认/拒绝调用同一服务端规则。
5. 验证：权限、来源变化、同目标竞争、历史不可复活、重放幂等、迁移及现有回归；实际模型质量与确定性规则分开报告。

### 人物更新接口（增量，保留现有路由）

在 `/api/v1/workbench/subjects/{subject_id}/profile-candidates` 下增加：

- `POST /updates`：`candidate_id`、`action`、`target_candidate_id`（非 ADD 必填）、`reason`、`time_text`（CHANGE 必填，可为模糊时间）。当前 owner 仅能使用当前有效候选；非 ADD 目标必须是同空间、同领域/种类的已确认理解。
- `GET /updates`：owner 专属建议和历史，包括实际来源版本。
- `POST /updates/{id}/confirm` 或 `/reject`：短事务检查材料和人物版本；已成功动作重放只返回历史，不重复应用。

ADD 确认新增候选；SUPPORT 保留目标结论/情境、合并来源到新版本，旧版本退出当前问答；CONFLICT 保留两方内容并使该理解等待核对，不删除无关记忆；CHANGE 将新理解作为当前版本并保留旧版与本人填写的时间说明。模型不会自动改事实。

新录音会使旧归纳过期。允许 owner 在四类更新确认中明确重新核对旧目标，但必须验证其所有原始证据仍是当前有效材料、文字与来源类型未变；无法验证则拒绝。撤权、删除或纠正失效的证据不可因此复活。

历史保存在追加的 0011 迁移中；旧候选确认接口禁止重启 superseded/conflicted 状态。实际更新会改变候选版本，参与问答发布后的来源校验；未生效的建议仅为审核记录，不进入模型输入，也不自行改变问答版本。读者看不到 owner 私有人物候选或冲突关系。SUPPORT 的材料数量不是独立经历数量或人格置信度。
