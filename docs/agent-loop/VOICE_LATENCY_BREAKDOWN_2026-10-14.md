这里是互不重复的等待拆分，不是所有组件的计算耗时相加：TTS已有部分与模型请求重叠；最后一项只包括尚未被重叠消除的合成等待、下行、播放缓存和首部静音。模型请求包括连接、传输、供应商排队和生成，不能称为纯模型推理。剩余处理是相减得出的合并项，不能全部算作审核或网络。

首个完整要点到完整结果结束仅26.447、0.944、1.256ms。该来源模式主要生成选段结构，随后由程序展开原话；所以 SSE 本身不会凭空省掉数秒。自由人物表达的首句收益需另测。

连续输入采用 Android AudioRecord → 20ms PCM → OkHttp WSS → ECS/Paraformer实时识别；语音回答固定使用当前授权材料的本地检索，微信生成后，小米普通音色流式输出至 AudioTrack。插话用当前客户端音量/持续帧检测，停止并flush播放，再取消服务器旧轮次；不是已集成的语义轮次模型。

已实际采用的开源组件包括 FastAPI、HTTPX、websockets、OkHttp、Sentence Transformers/PyTorch及BGE中文向量模型。Pipecat、LiveKit、Smart Turn、Silero VAD没有在这条已部署通话路径中接入。Android 原生 AudioRecord/AudioTrack/AcousticEchoCanceler提供采集播放能力；回声实际效果未由本次注入测试证明。

可参考的下一步：

1. 识别部分结果稳定后，预先准备本轮检索；最终识别与权限仍复核，不在每次临时字变化时重查。
2. 降低模型输入中的重复材料并保留修订/反例/必要上下文；在同组事实与未知题上比较，不按字数盲截。
3. 试验语义轮次判断。Smart Turn 官方支持中文和CPU，用于区分停顿与结束；不能只把400ms继续降小。https://github.com/pipecat-ai/smart-turn
4. 借鉴 LiveKit 的可取消预生成，先从检索预取开始，再单独评估提前模型/TTS的额外成本。https://docs.livekit.io/agents/multimodality/audio/#preemptive-speech-generation

以上下一步未在本次分析中实施。现有音频复用使第三轮更快；不能把这种收益推广为每个全新问题都能达到同样速度。网络各跳、首token、各次TTS起点等尚未全部独立测量，不能给出伪精确的独立毫秒数。
