# 语音 A/B/C 实测与判断

2026-10-14。代码基线 `34c8092`，本轮只新增隔离实验工具、测试及报告。生产 ECS、默认审阅策略和 Android APK 均未更改；没有推送 GitHub。

## 先看结论

取消阻塞式模型审阅能缩短部分等待；微信 `Deepseek-v4-flash` 实际支持 SSE。但当前来源问答主要让 LLM 输出很短的来源编号 JSON，然后程序复制原话，所以等待 JSON 收尾只剩很小的可重叠空间。要把自由分身回答改成“边组织句子边说”，还需要单独改造其生成协议，不能把这次编号流实验证明扩大到所有 Twin 模式。

最后一轮 4 题、每题 A/B/C，共 12 次调用路径，模型与首句合成均技术完成。**不含 ASR 停顿、资料检索和 Android 播放；不是手机两秒验收。**

| 模式 | 最后一轮技术完成 | 首 PCM 中位数 | 范围 |
|---|---:|---:|---:|
| A：保留模型审阅，允许既有 TTS 预备 | 4/4 | 3.534 秒 | 2.793–4.157 秒 |
| B：同选材/修复流程，仅取消语义审阅 | 4/4 | 2.574 秒 | 2.284–10.406 秒 |
| C：流式编号，完整首要点通过确定性校验即合成 | 4/4 | 2.255 秒 | 2.171–2.544 秒 |

首 PCM 是第一个声音块，不等于已经说出问题所需的核心要点。例如杯子题的第一句可能只是“自己买的”，原因在后一句。这里只衡量技术起播点，未把它称作“首个有效回答”或人工听感结果。4 题小样也不足以证明稳定的长期中位数或尾延迟。

同一轮 B 的杯子题首次请求超时，保留重试后用了 10.406 秒，没有把它丢出统计。C 四题都首次请求完成，成功路径较快，但不能仅凭它比 B 快约 0.32 秒就把差异全部归功于流式。

## 流式到底节省了哪一段

单次 SSE 能力检查：首 token 1825ms，首个完整 point 1954ms，完整 JSON 1955ms；收到 `text/event-stream`、真实返回模型 `Deepseek-v4-flash`、usage 和结束事件。

final 四题，首个完整 point 到整个 JSON 结束的间隔分别约 **27、19、19、26ms**。这是当前结构下能提前启动 TTS 的主要窗口。其余延迟仍在等待模型开始输出、TTS 首块和各次请求抖动；不是只需打开 `stream=true` 就能节省数秒。

普通音色 Xiaomi `mimo-v2.5-tts` / 白桦真实返回 PCM16。每轮只合成首句以观察起播路径，输出保存为 24kHz 单声道 WAV；并未逐句播放完整答案或在手机上听读。这轮也未测试真人音色克隆。

## 内容复核：不把模型审阅当裁判真值

人工复核这里指本轮开发审阅，非人物本人确认或真人用户验收。只读取冻结的授权核对文字，不以创作稿替换 ASR，不纠正输入后重跑以美化结果。

| 问题 | 输入材料与判断依据 | 最后一轮结果 |
|---|---|---|
| 喜欢喝什么茶 | 明确说喜欢淡一点、喝不惯太甜；没有具体茶叶品种 | A/B/C 都保留这个范围，没有编造品种 |
| 第一次独立跑十二路哪年 | 本人更正为 1987，不是 1986 | A/B/C 都选中更正；C 多带解释，事实未反转 |
| 旧杯子为什么留着 | 同一讲述有“看见她…想起收车后在站房喝水”、随后“所以…没急着扔”；代词“她”仍是输入瑕疵 | B 仅引“没急着扔”，未答原因，**不合格**。A/C 带回忆关联，但代词及归属仍需核对，不能据此称内容已完全准确 |
| 银行卡密码是多少 | 可用资料没有密码 | A/B/C 均 UNKNOWN；这是合理未知，不记作错误拒答 |

第一轮 A 的杯子题还出现：审阅正确发现选段没答原因，但建议 UNKNOWN 时忽略了可见的回忆线索。最终因请求预算不足失败，未发布。由此不能用“被审阅拒绝”直接证明原问题毫无材料。应分别登记：**引用是否存在、有没有回答问题、资料是否有歧义、审阅本身是否漏看**。

这也解释用户担心的误判：模型审阅有帮助，却不是可靠的标准答案。快速版的效果可以交给人比较，但去掉审阅不会自动提高事实质量；本次同时观察到快但漏答，以及审阅自身判断过严的线索。

## 实验方法、保护与局限

- 后端 `generate_answer` 按现有账号/有效性/consent 构造四题资料，在调用 AI 前截获到私有文件。各题 A/B/C 的 packet hash 一致；没有把测试答案放进模型输入。
- Weixin 端点与模型不变，`twin-quotes-v16` 与 response schema 不变。A/B 使用同一选材重试与结构修复规则，A 另执行真实语义审阅；B 不伪造审阅通过。
- A 使用已有草稿 TTS 预备，审阅完成前不计为可播放输出，避免把 A 人为拖成完全串行。
- C 是相同 schema 的增量编号解析；只在完整要点的引用真实存在后允许合成。最终 JSON、模型身份和结束事件仍检查。输出释放后发生错误记为 partial_failed，不假装声音可收回。
- C 对释放前的临时传输错误最多两次，释放后不重播；结构错误直接失败，没有 A/B 的结构修复。这是明确的实验区别，不能比较这类失败的恢复率。本轮 final 未触发 C 重试或修复。
- 真正的身份/撤权/来源版本最终复核仍在原后端路径。这些私有冻结材料实验不发布答案、不修改事实库，不能用它声称已验收实时撤权；把快模式接入 App 前仍要运行完整后端复核和迟到输出测试。
- 最后工具诊断修复（重试成功清除顶层旧错误、同一网络块错误前有效事件仍留痕）未改变成功路径提示词或业务输出；原始 final 结果保留，不重写时间。

## 验证与下一步

针对性回归 **55 项通过**：包括正式 quote/voice 上下文测试，以及新增 SSE 分帧、完整要点、未知来源、部分失败、A/C 取消、重试、合法引号包装和失败记录。没有以测试替身替代真实流式请求证据。

下一步优先顺序：

1. 将 B 作为明确的内测快速选项接入原有语音会话，保留确定性权限/来源规则；审阅可做抽样离线质量复盘。先解决当前“快但只读出无关引文”的例子。
2. 自由 Twin 表达使用独立的逐句协议，先生成一句完整、短且有用的回答，再接后续句；不能从 JSON 半句话取词、机械截断否定或把引用编号流当成人物自由表达已经完成。
3. 缩减每轮实际输入、会话预备和转述上下文，减少等待首 token；继而实测 ASR 轮次结束、TTS 首块及 Android 播放。只有这条链实测才报告“停说到有效回答约两秒”。
4. 录音豆声纹识别与语音速度分开推进，见 [SDK 核查](RECORDING_BEAN_VOICEPRINT_2026-10-14.md)。不把声纹分析加到每句回答的前置串行链上。

目前交付是可重跑的隔离实验及原始证据，尚未交付新的手机快速模式，不宣称正式服务器或 APK 已启用 B/C。
