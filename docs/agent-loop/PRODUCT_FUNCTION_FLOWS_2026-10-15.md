2026-10-15 核查版。用于会议、继续开发和制作使用介绍。今天核对了代码、既有验收记录和 ECS 运行版本；没有重新执行所有手机流程。历史实跑、当前入口和待完成项分开描述。

## 1. 产品要让用户获得什么

**留下一个人的故事，让亲友能够听见、理解、交流，并随着新讲述不断修正。**

需要展示三个具体效果，而不是“多个 Agent、八个分类、一个聊天框”：

1. 同一个人分几次讲述，故事可以连起来；修正年份后，之后的回答随之改变。
2. 一项人物理解能回到具体经历、条件和例外；本人可以纠正。
3. 亲友可以留下署名回忆，并收到只写给自己的话；不会把第三方评价偷偷变成本人事实。

连续语音让这些内容更容易交流，但来源查询、带特点的模拟回应、人物持续更新是不同能力，不能用一个语音演示代替全部验收。

## 3. 花田、八侧面、四视图分别表示什么

- **一片花田**：当前人物空间中，这个登录账号有权看到的故事。
- **一簇/一朵故事花**：一个已组织的故事入口，可连接多段讲述；不是强制“一段录音一朵花”。
- **一个花瓣入口**：故事中的记忆主题或内容分组，点开看正文、依据和原音；不是固定代表一种性格。
- **八个记忆侧面**：人生经历、人物关系、身份角色、偏好习惯、在意选择、感受状态、愿望牵挂、原话寄语。一项内容可以有多个侧面。
- **四个人物视图**：人生足迹、重要的人、在意选择、声音表达。它们把相同来源按不同问题组织起来，不是生成四个互不相干的人格。

当前代码用已确认、来源有效的故事/人物/观察/表达记录及维度映射选择内容；另显示已确认人物理解。它不是“每次打开页面都让 AI 凭空画四个画像”。内容形成需要提取与归纳，长期查找需要索引与检索；四视图本身主要是已有资料的组织与显示。

## 4. 可以直接用于使用介绍的流程

### A. 本人留下一个故事

1. 登录并进入自己的空间，在“今天”点“讲一段”。
2. 完成后先试听，确认声音保存，再选择转文字。
3. 核对名字、时间和错字。录音没有说过的新说明放到书面补充。
4. 确认整理后，在档案找到故事和记忆，点开听完整原音。
5. 有人物理解候选时，打开“人物”查看表述、条件与来源，再决定确认或修改。

遇到转写/整理失败，回录音库重试对应阶段，保留已保存声音。故事整理和人物归纳可能是不同后台任务，不能把“录音已保存”显示成全部完成。

### B. 亲友独立进入

1. 本人选择故事，在分享预览中核对完整录音范围，再生成邀请。
2. 亲友用自己的账号领取；本人确认接收账号后批准。
3. 亲友进入同一人物空间，通过花田、人物页或全部录音查看获授权内容。
4. 本人新增讲述后再次明确分享；撤权后亲友的新访问受限。

双方看到的花田可能数量不同，因为授权范围不同。10月13日云端快照中陈守义本人10段、亲友8段；这不是要求永久保持的数量，也不表示界面未同步。

### C. 查一件往事或和分身聊聊

1. 在“对话”选择“查找记录”，可以问具体往事；展开来源回到原音。
2. 本人开启理解与表达许可后，可选择“与 AI 分身聊聊”，询问新情境下的可能考虑。
3. 点“听这条回答”播放生成声音；“听原音”播放实际留下的声音，两者分开。
4. 点击“语音聊聊”进入一次连续通话，说话后等待回应，再继续追问；插话会停止旧轮次。
5. 通话页用“静音、暂停、结束”，字幕与相关故事按需展开。当前仍可能数秒等待或失败。

目前“来源查询快版”与“带条件的人物模拟”不是同一速度和质量等级。通话内容也不会自动全部写入人物记忆，要留下新故事仍走核对流程。

### D. 亲友补充另一个视角

1. 本人在“档案 → 亲友 → 亲友补记”开启对应亲友的补记资格。
2. 亲友选择亲身经历、他人转述或个人看法，输入文字或录音；录音转写后核对。
3. 可关联已有故事，署名提交。
4. 本人接受、保留不同说法或拒绝；需要分享时另外选择接收账号。
5. 作者与本人分别允许后，才可作为署名问答参考。接受补记不改变作者，也不自动生成已确认人格。
6. 撤回后停止使用该补记，相关派生理解需要重新核对。

演示重点应是“女儿的看法保留为女儿的看法”，不能只展示一条内容出现在列表里。

### E. 留一封专属信

在“档案 → 亲友 → 留给你”，选择已确认收信账号，填写文字或附加核对后的录音，保存草稿，核对后发送。收信人在自己的对应页面阅读或听信。本人可以撤销后续访问。当前是指定账号留言，不演示为自动身后开放。

### F. 本人纠正分身理解

输入问题 → 选择“先录下我的回答，再对照” → 等 Twin 答案锁定 → 本人录下回答并核对 → 查看差异 → 本人决定如何补充/修订 → 确认新理解 → 同题及改写题复问。

最后两步是产品效果验收重点，需要同时检查人物页和回答变化。比较要区分事实、考虑因素、条件和表达；换个合理说法不是答错，没有依据也不能强行评分。

## 5. 下一步开发以四个可见结果交付

| 顺序 | 要交付的结果 | 具体检查 |
|---|---|---|
| 1 | 同一道有条件的问题回答完整 | 杯子保留原因、1987纠正及旧记录解释不漏；未知与故障分开；保留全部轮次 |
| 2 | 连续语音更快而且不抢话 | 已知事实、人物模拟和复杂回忆分别计时；真正连续追问，不以含完整关键词的独立题代替 |
| 3 | 人物理解能实际变化 | 旧回答→本人补充→候选确认→同题和改写题变化；无关事实保留 |
| 4 | 多视角与专属内容独立可用 | 亲友录音补记→处理→署名引用→撤回；指定信→正确账号可见→其他账号不可见 |

每一项都同时检查服务端结果和 Android 用户操作。完成后录一条连续使用介绍，而不是只拼截图或罗列接口。复杂实时链路可以隔离试验，但不能让原有记录、授权和花田任务随模型实验一起失稳。

## 6. 使用介绍的顺序与文案原则

建议依次演示：留下故事 → 花田找到它并听原音 → 人物理解及依据 → 亲友获授权 → 带记忆连续对话 → 本人纠正后再问 → 亲友补记 → 专属留言。

首屏只告诉用户能做什么、下一步在哪。保留“AI分身、本人原话、待核对、仅自己可见”等必要短标签；来源版本、技术复核、模型指纹和验证说明进入技术报告，不成为日常界面的小字。代码中仍有一些长授权说明及来源枚举展示，本次仅识别，文案整改未实施。

正常体验与验收说明分开：演示视频可以清楚讲用户任务，配套报告再记录版本、输入方式、实测等待和未通过项。未实跑的环节不拍成已完成。

## 7. 本次核对的实现入口

- `apps/android/app/src/main/java/me/remember/app/integration/NativeWorkbenchScreen.kt`：导航、两种问答、分享和来源。
- `MemoryMap.kt`、`NarrativeScreen.kt`：八侧面、四视图、理解与审核。

- `VoiceCallScreen.kt`、`VoiceCallEngine.kt`、`CalibrationScreen.kt`：通话、播放控制与校准。
- `services/backend/app/api/voice_sessions.py`、`voice_turns.py`、`api/twin.py`：线上语音编排、资料授权与回答。
