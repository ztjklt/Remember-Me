# 第二轮继续优化：来源上下文、逐项回答与手机故事跳转

日期：2026-10-09，北京时间。基线 `87d88a4`；工作区 `D:/codex_work/remember-me-agent-loop`，分支 `codex/agent-integration`。这是前一份 [第二轮验收](ROUND_TWO_ACCEPTANCE_2026-10-09.md) 的增量，不覆盖其失败记录。

**结论：修复了证据传递丢失上下文、复核对象与实际输出不一致等程序问题，补齐人物到关联故事的手机入口。真实60问仍未全部合格，新问答协议只在本地评估环境开启，没有替换ECS。**

## 用户现在能看到的改变

1. 在“重要的人”“在意与选择”中，已确认内容如果与已确认故事共用原文依据，可直接点“读故事”，继续阅读和打开完整原音。没有共同来源就不制造关联；不按共现次数推断亲密度。
2. 故事弹窗使用当前状态中的真实记录。撤回、来源变化后不继续使用缓存的旧故事；测试观察撤回后，网页对应入口实际消失。
3. Android故事、编辑与历史长文区域显式使用不透明主题底色，保留自然背景与品牌；200%字号下仍能返回和打开原音。原生弹窗过渡帧与稳定画面分别识别，截图不再只依赖Compose空闲。
4. 评估用问答按问题要点组织：每一项分别选择来源、判断已知与未知。程序复制原话；混合回答明确标记引用，不把原话中的“我”冒充系统本人。模型审查检查最终成文。

这批关联是“共同原文依据的故事入口”，不是自动合并人物、自动确认同名人物或已经完成复杂关系图。

## 根因与实现

原后端构造Twin请求时丢弃录音编号、讲述日期、原文字符位置及修订时间语境；排序后的孤立引文让模型更容易误解代词和前后补答。

内部证据增加可选字段，来源仍先经过原有权限与有效性过滤。只补元数据，不重读私密邻段或整篇原文。书面补充不冒充音频对齐；讲述日期与事情发生日期明确区分。现有来源指纹不因增加传输字段被全部废弃。

新增实验开关 `AI_TWIN_STRUCTURED_ANSWERS`，默认false。启用后每次生成1–4个要点并校验来源、姓名原字形和输出边界；第二次模型调用逐项审查支持、完整性、归属、时间和回答类型。无效结果明确失败，不静默重新抽样，不转成假UNKNOWN。此审查仍由同一个模型执行，不能代替独立语义验收。

公开TwinOutput与数据库不变；内部兼容扩展、先AI后后端的升级顺序见 [接口提案与执行账本](../architecture/twin-context-refinement.md)。没有增加模型供应商、放宽引文或授权校验。

## 真实模型结果：返回不等于正确

复用原有三人30段材料、现存真实ASR及技术确认。没有重新合成音频、没有跑新ASR、没有用gold覆盖ASR、没有宣称人工听读或真人认可。

端点保持微信 `https://chatapi.weixin.qq.com/openai/v1/chat/completions`；请求和响应标识均为 `Deepseek-v4-flash`。非流式json_object，本地完整校验，串行、45秒配置。标准答案不进入模型输入。

| 实验 | 范围 | 返回 / 失败 | 说明 |
|---|---|---:|---|
| context-v8 | 7个既有问题 | 3 / 4 | 仅补上下文仍会合并未经确认的字形 |
| points-v1 | 同7问 | 4 / 3 | 逐项协议仍有名字与语义问题 |
| points-v2 | 完整60问 | 49 / 11 | 49只是返回数；存在5个已识别的答案层问题 |

v2分人物：公交司机17返回/3失败；消防员16/4；人生回顾16/4。11个失败为bus_driver-q02/q09/q10、firefighter-q04/q12/q13/q19、life_review-q02/q03/q04/q08。均保留错误记录，未保存为成功答案。

已识别的答案层问题：

- bus_driver-q04：加入未询问的铁路工作说明，归属与必要性需复核。
- firefighter-q01：系统生成回答使用第一人称。v3已用第三人称，并回引4份实际来源；来源明确支持值班后致电妈妈许燕。
- firefighter-q03：无必要地使用男性“他”，不应从第一人称转写猜测性别。
- firefighter-q20：读者材料未提供手机静音原因，正文说未知却标SIMULATION。v3此次被姓名锚点校验拒绝，仍未交付合格答案。
- life_review-q20：同样存在未知原因标签错误。v3正确返回UNKNOWN，不暴露未授权的后续解释。

另外44份返回答案已阅读，但没有完成独立逐事实和原音核查，因此标为 `not_fully_verified`。不把它们计为“44份准确”。纠正年份、过去与现在住址、第三方转述、否定与未知问题中出现正确案例；仍不能外推为稳定准确或全部隐私场景已经验收。

本轮逐项协议v1–v3共有128条真实供应商请求元数据（74次生成、54次审查），报告usage合计1,182,935 tokens；不包含旧协议v8请求，不换算费用、不作性能承诺。提示词版本/哈希、端点、HTTP状态、模型标识、耗时、usage和finish_reason在 `context-provider-calls.jsonl`。模型失败后无自动再抽样。
