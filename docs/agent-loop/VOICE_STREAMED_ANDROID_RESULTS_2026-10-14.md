## 本次做了哪些优化

1. 微信采用真实 SSE，首个完整要点通过结构和来源选择检查后，提前准备首句合成。完整 JSON 与后端资料版本检查完成后才放行音频；没有把未闭合 JSON 或任意半句话直接念出。
2. C 的普通识别停顿从 800 ms 调到 400 ms；简明模式仍为 1400 ms。真实收尾还受识别和网络影响，表内实际约 594—684 ms。
3. 本通话复用有效材料，版本、身份、可见范围和模型同意发生变化时重建；不缓存模型答案。仍每轮检查授权，生成及播放阶段检查来源变化。
4. 复用小米 TTS 连接；同一句正在合成时不反复取消重启。缓存本通话内完全相同且成功合成的 PCM，最多8条/2 MB，关闭通话即清空。
5. 来源模式允许对当前获授权的首条候选原话做一次私有预合成，与模型生成重叠。最终首句逐字相同才用，否则丢弃重做。此机制不替模型选择答案，不把推测音频发给手机。
6. C 使用精简语音提示词 `twin-voice-quotes-v1`，A/B 保持原提示词。因而不是只改变 `stream=true` 的严格消融，不能把所有速度变化归给 SSE。
7. Android 实际收音和测试注入共享 PCM/VAD/打断路径，迟到的旧轮次不能恢复播放。测试每50 ms记录播放帧，录像按实际播放进度保留句间等待、排除打断后未播放的声音。

独立大模型语义审阅按用户选择从 C 中去掉；结构、原文逐字存在、来源、权限和版本规则保留。普通文字和校准不随 C 改变。详细契约见 [语音增量契约](../architecture/voice-streamed-contract-20261014.md)。

## 没有把失败藏起来

所有轮次保存在相应 `var/voice-streamed*` 目录。下面的协议首包与上面的手机首声口径不同，不能混为同一速度指标。

- 第一候选隔离试验：首包 3.719/3.282 秒；加入有限预合成后 1.518/2.847 秒。较快的单次结果没有作为最终手机结果。
- 第一候选 Android 三轮通过，输入结束到起播 3.747/3.390/3.157 秒。
- 第二候选试过跨请求微信连接复用：五题协议首包 2.482/10.603/3.404/2.520/2.489 秒，其中一次超时后重试。随后 Android 前两轮完成，第三轮出现两次响应头超时并失败，保留录像和日志。
- 尚不能断定超时由连接复用导致；最终撤销这项实验，恢复单次请求管理微信连接。TTS 仍按通话复用。
- 最终候选隔离三题全部完成，首包 5.635/2.146/3.454 秒。最终手机三轮是本报告上表；这说明仍有供应商/网络/生成波动，不能宣称消除超时或稳定两秒。

## 内容与体验复核

- 第一轮引用了首次跑12路的工作经历、1987年更正和他人协助准备；没有恢复已更正的1986年结论。但选了三段长引文，仍然啰嗦，不能视为自然简短聊天完成。
- 第二、三轮引用喜欢淡茶、太甜喝不惯的本人材料，连续追问没有跳到另一个人物。
- 第二轮“先不说工作了”被识别成“钱不说工作了”并提前结束一小轮；随后的真实问题触发取消，错误前缀没有播出。400 ms 的取舍确实会增加拆句风险，语义收尾仍需改善。
- 本次是来源问答 `mode=evidence`。人物模拟路径已有相同流式接线及确定性回归，但本录像不能替代其内容质量验收。
- 画面来自真实 Android App，走公网 HTTPS/WSS 调 ECS，没有 ADB reverse/SSH 业务隧道。Paraformer、DeepSeek、小米均真实调用。
- 为绕过模拟器虚拟麦克风静音故障，instrumentation 按实时20 ms节奏把预录声音送入 App PCM/VAD 入口；没有注入识别文字或预写答案。生产安装包不包含测试数据入口。
- 视频声音取自本轮输入与 App 收到的输出 PCM，依据 AudioTrack 进度同步；不是物理扬声器录音。实体麦克风、扬声器回声、耳机、慢速讲话仍未验收。

## 尚需继续压缩的环节

1. 识别结束前准备可取消的检索，但最终只用最终识别和当前授权验证后的材料；先测是否省掉约0.4—0.7秒，避免多次试探查询放大资源消耗。

3. 供应商生成和连接尾延迟仍是主要不稳定项；分别统计新问题/相同句复用、冷/热调用与超时，不能以一次2.1秒首包替代手机效果。
4. 实体 Android 做真实收音、回声、耳机及慢速停顿验证。本轮不以模拟器注入证明声学体验。

本轮交付是可连续追问并插话的优化试验版，最终三轮数字首声为2.55—4.26秒；“稳定约2秒”保持未达标。
