# 三条语音路线：本轮比较与选择

日期：2026-10-15。建议：**当前可用版本继续采用微信 DeepSeek + 小米 TTS；低延迟路线继续验证 StepAudio 3 Realtime；暂不将主办方 DeepSeek-V4.1-Flash 替换为实时主路。** 本轮没有修改正式模型、服务配置或 APK，没有推送 GitHub。

## 三条路线具体是什么

1. StepAudio 3 Realtime：持续音频输入 → 模型调用记忆工具 → 语音回答。本报告的 Realtime 指它，不是主办方 DeepSeek 的一个语音模式。
2. 主办方网关 `hackathon/v_model/deepseek-v4.1-flash`：Paraformer 识别 → 记忆准备 → 文字模型 → 小米 TTS。实际返回模型标识为 `deepseek-v4-1-flash-260910`。
3. 原有微信 `Deepseek-v4-flash`：与第二条相同，替换的是文字模型入口。两种 DeepSeek 都不直接生成音频。

语音聊天快慢与事实可靠性是两项指标。版本号、接口返回成功、引用真实，都不能单独代表答案准确。

## 刚刚补跑的同 TTS 对照

使用同一 ECS 出口、陈守义同一份冻结授权材料、七个问题各三轮，两种模型交错请求，共 42 次。七题为公交故事、茶偏好、茶浓淡追问、1987 年份纠正、旧 1986 记录原因、未知密码、旧杯子原因。没有裁剪事实、否定、修订或条件。

- 两方逐题消息内容与提示词相同，程序检查了全部对应消息哈希。
- 共用已部署的引用选择提示词与 `render_ids` 校验；不做额外大模型语义审阅，不自动重试。
- 每次文字请求最多 12 秒。两方均请求 2048 输出 token 与 `thinking.type=disabled`；主办方另请求 `reasoning_effort=low`。参数意图相同不代表路由实际推理模式相同。
- 2048 预算用于避免旧实验的 512 token 被思考耗尽；它不是要求回答写 2048 token，也不保证完成得更快。
- 所有成功文字答案调用同一个 `mimo-v2.5-tts`“白桦”音色；关闭音频缓存，保留原始 PCM、各块到达时刻和音频开头静音。
- 使用独立脚本与连接池，结果不是原封不动重跑当前 Android 通话。没有新执行麦克风、ASR、动态 RAG 或撤权流程。

| 指标 | 微信 DeepSeek | 主办方 DeepSeek-V4.1-Flash |
|---|---:|---:|
| 请求次数 | 21 | 21 |
| 返回并通过结构/来源校验 | 20 | 16 |
| 12 秒内未完成 | 1 | 5 |
| 文字回答中位数 | 1.198 秒 | 4.293 秒 |
| 文字回答 P95 | 6.229 秒 | 10.487 秒 |
| TTS 可听起点估计中位数 | 0.761 秒 | 0.760 秒 |

| 同上 P95 | 6.949 秒 | 11.172 秒 |
| 成功请求最慢的上述等待 | 12.527 秒 | 11.172 秒 |

**计时范围**：从材料已准备好、发起文字 API 开始，到服务器收到的音频按块播放时预计出现首个有声帧。包括模型、校验、TTS 网络及 30ms 播放缓冲；不含用户停顿判断、ASR、实时检索、ECS 到手机及扬声器延迟。不是完整手机“说完就听到”的时间。

可听起点用 10ms PCM 窗 RMS > 200 和实际分块到达时间推算，保留断流等待及前导静音。两阶段中位数不能直接相加代替逐请求总耗时。所有延迟统计仅对成功请求计算，P95 采用 nearest-rank；超时单独保留，不能算成正确 UNKNOWN。21 次只是七个开发问题重复，不能推导普遍稳定性。

微信超时：第 1 轮公交故事。主办方超时：三轮旧杯子、第 2/3 轮公交故事。微信也有 11.768 秒才返回文字的长尾，因此这里的“保留微信”不表示现有版本已经稳定两秒。

### 主办方为什么更慢

本轮主办方成功回答仍报告思考 token。例如第 1 轮公交故事，799 个输出 token 中有 775 个思考 token，首正文约 9.633 秒、文字校验完成约 9.729 秒。第三轮浓淡追问文字约 8.305 秒。后续 TTS 并没有相应变慢。

官方支持思考开关与强度参数，但**本次通过主办方网关请求关闭后，仍观察到思考用量**。尚不能确认是参数没有透传、路由约束还是其他映射，需向主办方确认实际支持的非思考配置。没有原始服务端追踪，不能把全部等待精确归因为推理、排队或网络。[DeepSeek 官方参数说明](https://api-docs.deepseek.com/guides/thinking_mode/)

本轮也保留了双方缓存用量；不同提供商实际缓存命中不同。因此这比较的是当前可访问的“模型、网关、配置与连接”组合，不是同一硬件上底层模型的纯计算速度。

## 内容效果与判决规则

以下是助手对照原材料的逐题审阅，不是独立人工评测，也不是未见过的留出集。引用校验只保证选段来自输入；内容判定还检查是否回答所问、时序正确、归属清楚和未知边界。

| 路线 | 整题合格 | 部分回答 | 内容不合格 | 请求失败 |
|---|---:|---:|---:|---:|
| 微信，本轮 | 17 | 3 | 0 | 1 |
| 主办方，本轮 | 15 | 0 | 1 | 5 |
| Realtime，前一组初版试验 | 18 | 2 | 1 | 0 |

三个判断例子：

- 问“喜欢什么茶”：答出喜欢淡一点、不喜太甜即可；没有说具体茶叶品种，不应整题拒答。主办方第 3 轮完全返回“现有记录还不足以确定”，判不合格。
- 问“为什么旧记录写 1986”：讲清记混相邻年份、后来查看证件发现错误，可以合格；不强制重复没被问到的所有数字。不能把旧记录仍当作当前事实。微信第 3 轮只解释“看证件后发现年头记混了”，仍按实际问题判合格。
- 问“旧杯子为什么一直留着”：原文有看见杯子想起站房喝水、一天忙完，以及“所以没急着扔”的连接。微信三次只选“没扔”或杯沿缺口，没有解释记忆关联，判部分回答。主办方三次均超时，不能当作它答错了具体内容，也不能当作它答对。

故事题只要求一个有依据、时间不矛盾的故事，不要求把全部记忆都复述。茶的个人口味不得扩展成健康规定；明确没记录密码时 UNKNOWN 合格。故事中没有解释清楚的“他”等指代保留为表达改进项，不因不影响所问事实的措辞瑕疵把整题判错。

这些小样本未证明三家模型的普遍准确率高低。尤其本轮主办方超时集中于故事和原因题，不能只对剩下的简单成功题算准确率，再宣称它更准。

## Realtime 的速度应怎样放在一起看

前一组同七题三轮、同记忆包的 StepAudio 3 Realtime 结果：

- 21/21 返回。
- 输入讲话结束 → ECS 首块回答音频：中位 1.968 秒，P95 3.231 秒。
- 保留音频前导静音及分块播放后，可听起点估计中位 2.384 秒；仍不含服务器到手机链路。
- 初版有三次旧杯子解释不足；增加通用“明确的上下文因果可以归纳，先答已知”规则后，对杯子、年份、未知各三次回归 9/9 符合要点。这九次不能与初版混算，也不是新题泛化成绩。

**2.127 秒与 2.384 秒不能直接比较大小**：微信本轮从文字请求开始；Realtime 从说完开始，已经包含自己的收尾与识别环节。Realtime 的工具在实验中返回预先冻结的材料，不进行新的数据库检索；其输出是自然语音，文字两路线则按引用选择协议生成。它们也不是同一个输出协议或完整手机环境。

Realtime 有更接近两秒的架构与本项目试验结果，但正式采用仍需完成真实授权检索、资料变化与撤权清理、断线恢复、生成中取消，以及 Android 麦克风、回声、耳机和真实网络测试。当前没有哪条路线已证明稳定两秒。

## 建议采用方式

1. **当前体验保留微信 + TTS**：本轮响应与完成率优于主办方入口，既有权限和来源路径已接入；继续修复原因漏答及长尾。
2. **低延迟研发优先 Realtime**：下一次应把它接到同一真实授权检索和 Android 音频链路，测完整用户等待时间，不以冻结工具试验直接替换正式版。
3. **主办方 Flash 保留候选**：先确认有效的非思考配置，再复测。若考虑用于离线记忆或人物分析，需另测那些任务，不能从此次引用选择测试推断分析质量。
