## 实际视频

本机文件：`services/backend/var/voice-demo-20261014/actual-demo/android-voice-demo.mp4`。约 19.17 秒，1 倍速，保留提问、全部等待和完整首轮回答。来源为 `take-08`；原始屏幕录制、协议事件、音频与失败尝试均保留在被忽略的 `var` 目录。

- Android 0.11.0-internal 直接连接公网 ECS；未使用业务隧道或电脑代替服务器转写。
- 输入为已有合成提问，通过模拟器麦克风送入 App 的实际收音和 Paraformer 流程。
- 回答为本轮真实服务器结果，保持现有模型审阅，使用小米合成。
- 视频声音取自 App 本轮收到的 PCM，按 AudioTrack 实际播放进度对齐；不是物理扬声器外录，也不是预先准备的回答。
- 屏幕与事件使用 screenrecord Winscope v2 时间信息对齐；主机与设备时钟采样往返约 51 毫秒。因此毫秒数用于排查，不代表物理声学延迟的同等测量精度。

## 失败与修复

保留 take-01 至 take-09 的原始记录。早期尝试遇到模拟器音频读取故障、输入通道启动顺序问题，以及 instrumentation 未推进 Compose 时钟导致字幕画面不刷新。工具改为预先连接虚拟麦克风后重新打开 AudioRecord，并在字幕变化后等待界面刷新。

take-05 首轮约 14.5 秒，服务器日志存在模型请求超时后重试；take-06 首轮约 5.9 秒，但画面刷新和第二句识别均未通过。这些结果没有用于替换 take-08 的可观看验收片段。

take-09 再次测试两轮，首轮返回，第二句没有形成新识别，最终 AssertionError；此前同类尝试伴随模拟器音频读取错误。尚不足以单凭这些结果认定真机存在同样问题，也不能据首轮成功宣称连续对话合格。最终视频明确只展示首轮。

新增 `record_phone_demo.py` 与 `render_phone_demo.py`，记录协议和播放时刻，导出原速计时视频。修改仅在 Android instrumentation 测试路径。测试 APK 构建通过，两份 Python 工具语法检查通过，工作区 diff 空白检查无错误。

## 录完后的发言人归属

采用现成预训练说话人模型进行集成验证，不自行从零训练。SDK 负责录音与传输；后端需完成音频排序解码、说话人分段、文字时间对齐、身份建议与人工确认。没有注册样本时先显示“说话人 A／B”；用户确认后分别进入本人讲述或亲友署名补记。

本轮仅核实 SDK 与实现边界，尚未实现或验收自动声纹归属。它不进入每轮实时接话的阻塞流程，也不作为登录或托付解锁凭证。详见 [SDK 核查](RECORDING_BEAN_VOICEPRINT_2026-10-14.md)。

后续应分别推进：将已同意的快速／流式路径接入手机后按相同口径计时；验证连续输入与打断；离线归属先接预训练模型及人工确认，再等待实物验证 Opus 编码与多人录音质量。不能用合成声音实验替代真人声纹准确性验收。
