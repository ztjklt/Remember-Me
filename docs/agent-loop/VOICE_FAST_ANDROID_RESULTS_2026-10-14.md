# 快速语音进入 Android 与 ECS：实跑、计时及剩余差距

本轮已将用户批准的 B 路径接入实际语音会话：保留现有模型和来源规则，省去阻塞播放的独立语义审阅。Android 可在开始通话时选择“快速回复”，关闭则使用原审阅路径。ECS 已切换候选发布；没有推送 GitHub。

**完成的是带记忆的连续问答与播放小样，不是两秒自然实时对话验收。** 本轮最终两组各两轮全部运行完；快速版起播 3.284 / 4.861 秒。声纹算法、实体手机麦克风和扬声器回声未在本轮验收。

## 视频到底验证了什么

使用真实 Android 应用，经公网 HTTPS/WSS 调用 ECS 的 Paraformer、微信 Deepseek-v4-flash 和小米白桦音色。没有 ADB reverse 或 SSH 业务隧道，没有注入识别文字、预写答案或伪造服务器返回。

本轮模拟器系统音频输入多次失效：AudioRecord 仍在读，但接到的 PCM 全是静音，系统日志出现 Tinyalsa `pcm_readi` I/O 错误。为避免继续反复重启，最终录屏使用**仅在 instrumentation 测试中的 PCM 输入替换**：把预录问题按 20ms 实时节奏送入 App 已建立的真实 WebSocket，绕过模拟器 AudioRecord。生产 APK 不包含这个测试入口。

屏幕是实际 App 录屏。视频中的声音取自本轮输入文件及 App 实际收到的回答 PCM，按设备时钟和 AudioTrack 播放进度同步；不是扬声器外录。screenrecord Winscope v2 元数据用于对齐画面，未加速或删除等待。音频数字同步不能替代物理声学测量，也不能证明没有扬声器回声。

两轮分别是“你喜欢喝什么茶？”和“刚才说的茶浓一点还是淡一点？”，第二轮在上一轮播完后提问。因此证明了连续两轮与承接问题，**不构成本轮真人插话打断验收**。本次运行的是 `mode=evidence`，不能用它替代条件化人物模拟回答的质量验收。

## 最终同版本小样

同账号、同人物、同两份输入 WAV、同供应商/模型和同一有效资料版本。先标准版、后快速版，各执行一次完整两轮，不挑选某一条替换；并非随机化大样本实验。两轮中的模型措辞与引文选择可以不同，后续上下文也随真实回答变化。

| 项目 | 审阅版第1轮 | 审阅版第2轮 | 快速版第1轮 | 快速版第2轮 |
|---|---:|---:|---:|---:|
| 输入音频送完 → 手机文字出现 | 12.204s | 10.091s | 2.525s | 3.492s |
| 输入音频送完 → AudioTrack 起播 | 12.337s | 10.227s | 3.284s | 4.861s |
| 输入结束 → 最终识别/开始回答 | 0.582s | 0.898s | 0.668s | 1.115s |
| 资料准备/检索 | 0.470s | 0.498s | 0.460s | 0.680s |
| 文字到达 → AudioTrack 起播 | 0.136s | 0.140s | 0.765s | 1.372s |

快版模型生成实调用时分别为 1.140s、1.445s，各调用一次，日志明确 `semantic_review=skipped`。审阅版第一轮是**生成请求**等待约8秒后重试，随后审阅；第二轮生成约0.772秒、审阅约7.699秒。之前探索轮也出现过审阅超时重试。取消审阅能去掉这一串行步骤，但不能解决生成请求本身的网络/服务波动。

PCM 开头到首个明显能量窗口约 0.10—0.14秒（20ms 窗口 RMS>150 的诊断口径），所以起播数字不是准确的物理“听见第一个字”时刻。两个快速结果按这个粗略口径约3.4秒、5.0秒才出现明显声音。没有用“嗯，让我想想”充当有效回答。

在最终比较前，快速探索组另有6.375s、4.118s；标准探索组有13.820s、5.445s。全部保留。**不能从最终两题声称普遍提速百分比、稳定中位数或已达到2秒。**

## 内容检查及保留的边界

四轮均回答喜欢淡茶、太甜喝不惯，所引文字来自当前可用的本人材料；“刚才说的茶”没有归属到其他人物。标准版第二轮出现重复引用、回答较啰嗦，已登记。这两题只能验证这一具体事实与追问，不是原60题或人物模拟质量全面通过。

快速模式仍执行：身份/故事权限过滤、合法结构、真实来源编号、原文逐字存在、生成后资料与权限版本复核，以及播放前/期间的来源检查。**它不再执行独立模型对相关性、漏答、否定和人物归属的语义复审**，因而这些方面的质量风险需要另测，不能称作“审阅通过”。校准报告保持标准路径。快速人物结果不伪造 coverage / omitted_points。

`/persona/voice-fast` 已有实现和确定性回归；本轮使用公交司机样例做人物模式实际调用时返回 REQUEST_INVALID，未进入模型。其可用人物资料前置条件需单独定位及验收；不能把来源问答视频算作该模式通过。

## 修改与检查

- AI 增加私有 fast 路由与请求级审阅策略，默认行为仍为审阅；普通文字请求不会被快速语音策略污染。
- 后端能力查询、创建会话、轮次事件记录实际模式；原接口字段可兼容旧客户端。
- App 增加快速回复开关，保留校准和原录音入口。缺少服务能力时明确提示，不静默冒充快速结果。
- AI 针对性回归82项通过；本地后端39项通过；ECS 隔离 PostgreSQL 环境30项通过（含迁移、会话和回答相关用例，纯逻辑用例不访问数据库）。
- APK及 instrumentation 构建、安装通过，签名验证通过。最终两个完整两轮 instrumentation 均 `OK (1 test)`。

失败记录保留：`phone-01`—`phone-04` 的虚拟麦克风/模拟器故障，首次阶段部署的 RAG 模型缓存路径错误及修复，`app-pcm-reviewed-01` 的脚本误点。脚本最初选择了页面后方的分身开关，修改了样例偏好并导致通话没开始；已改为仅选择弹窗内的开关，通过正常 API 恢复原 enabled=true，保留增加后的版本号。恢复过程见 `preference-restoration.json`。最终 `paired-*` 比较在恢复后进行，两组 `source_version` 相同。历史答案按既有失效规则处理，未回滚版本或恢复失效答案。

## 还需要做什么

1. **真正的首句生成播放**：当前 B 仍等完整合法答案；C 的来源编号流只是此前隔离实验。此前首 point 到 JSON 收尾仅19—27ms，不能靠打开 stream=true 就省掉数秒。自由 Twin 需要单独设计“完整语义单元、必要条件及来源先就绪再播”的生成协议，处理后续失败和取消。
2. **减少可重叠等待**：识别结束前准备可撤销的检索结果；复用连接并量化模型首 token、TTS 首块和手机缓存，优先降低尾部波动。当前权限与来源变化检查继续保留。
3. **真实收音验收**：最终 PCM 替换绕过了本地音量判断和回声路径；拿实体 Android 验证慢速讲话、停顿、插话、扬声器和耳机，不能以这份录屏代替。
4. **录完后的发言人归属**：SDK 只提供音频，采用预训练说话人模型集成，不从零训练；排序/解码、分段与ASR对齐、未知身份、人工确认和撤回仍待实现/验收。本轮未将算法塞入实时聊天链路，也未宣称自动声纹识别已经可用。
