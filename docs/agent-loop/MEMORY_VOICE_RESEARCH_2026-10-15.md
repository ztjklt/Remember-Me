# 长期记忆与快速语音：技术核查与产品取舍

日期：2026-10-15。范围：官方资料调研、Step 模型目录实时查询、现有代码和 ECS 只读核对。没有新增模型推理测评、修改线上服务、构建 APK 或推送 GitHub。下文的速度来自已留存的实验，不是今天重新测得。

## 1. 判断

长期记忆与快速语音并不矛盾。已有开源框架把持久记忆、检索和语音流水线接在一起。但“支持这些能力”不等于在我们的中文、来源修订、亲友授权和手机网络条件下稳定两秒接话。

应区分三件事：长期保存多少资料、本轮需要读取多少资料、必须等待多少串行工作。长期资料多，并不要求每轮把整个档案交给模型。人物归纳、记忆写入和复杂比较可以在通话之外完成；通话读取已经整理好的有效资料。

产品目标仍是“本人留下并掌控经历，亲友能了解、聆听、交流并补充”。快速说话是体验要求；能用对这个人的记忆、条件和变化，才是核心差异。

## 2. 已有方案到底证明了什么

| 方案与原始资料 | 已提供的机制 | 对本项目的价值与边界 |
|---|---|---|
| [LiveKit：外部资料与 RAG](https://docs.livekit.io/agents/logic/external-data/)；[Supabase 记忆示例](https://livekit.com/blog/supabase-voice-agent-memory) | 会话前载入用户资料；回答前检索；数据库保存记忆，按用户隔离 | 证明记忆可以接入语音。提前检索可省掉“模型先决定查库，再调用一次模型回答”的额外往返；示例不证明我们的端到端时延 |
| [Pipecat 官方 Mem0 示例](https://github.com/pipecat-ai/pipecat/blob/main/examples/rag/rag-mem0.py) | 在识别与 LLM 之间放记忆服务，连接 STT、LLM、TTS；支持云端或本地记忆配置 | 可以借鉴管线与取消机制。其记忆写入规则不能直接代替本项目的本人核对、亲友署名及撤权机制 |
| [Letta Voice](https://github.com/letta-ai/letta-voice/blob/main/README.md) | LiveKit 语音连接，Letta 持久状态、记忆和工具执行 | 证明有状态的语音 Agent 有现成实现。工具数量和后台记忆管理仍可能增加等待，并非换框架即更快 |
| [StepAudio 3 Realtime](https://platform.stepfun.com/docs/zh/guides/models/stepaudio-3-realtime) | 双向语音、话轮管理、打断、工具调用 | 值得与当前组合式链路做隔离比较。官方“极低延迟”未给出本项目相同资料、权限和问题下的成绩；当前未接入或实测 |

没有找到足以证明“完整满足我们的所有要求，而且中文手机通话 P95 稳定小于两秒”的公开同条件证据。这不意味着不可行，也不能因此宣称已经有现成产品可直接替换。

豆包 App 的内部运行配置不在本次证据范围。不能把公开实时接口、单段演示或首句招呼的速度当作其私有架构及长期记忆性能的证明。

## 3. 如何减掉等待，而不减掉关键记忆

### 3.1 把工作放到合适的时机

| 时机 | 应做的事 | 保留的约束 |
|---|---|---|
| 故事核对后 | 提取事实、索引、故事关联、人物候选；处理纠正与例外 | 原音、机器稿、核对稿和书面补充分开；候选不能自动替本人确认 |
| 进入通话时 | 准备当前读者可用的少量人物理解、近况和相关原话；预热连接与检索服务 | 缓存绑定身份、人物空间、来源及授权版本 |
| 用户正在说话 | 对稳定的临时识别内容预取候选；复用已准备的资料 | 临时结果只帮助找候选，最终问题要重排并补齐条件；不让前半句代替完整意图 |
| 讲话结束后 | 完成选材，保留人物归属、否定、时间、修订及反例；形成可独立成立的首个回答单元 | 不把“还没找到工作证”与后来的“已找到并纠正年份”并列为当前状态 |
| 开始回答后 | 合成并播放已通过对应检查的内容，同时准备后续；允许打断 | 旧轮次、撤权资料和失效音频不能继续播放；未播完内容不冒充用户已经听到 |

这里的“精简”是减少重复结构和无关材料，不是按字符截掉最后一句否定，也不是把上下文只压成“节俭、顾家”几个标签。

### 3.2 不能简单打开两个开关

[LiveKit 的提前生成机制](https://docs.livekit.io/agents/multimodality/audio/)会在确认用户结束前开始 LLM，TTS 也可选择提前准备。但最终上下文或工具改变时会丢弃草稿并重新生成。因此“先开始生成，再补 RAG”可能反而多花一次调用。需要先使材料准备与话轮判断协同，再测是否真的减少用户可见等待。

本项目此前提前检索实验的最终问题没有命中临时问题缓存，输入精简只减少约 3.1%—5.5% 的可比较样本 token；没有证明更快，候选已回退。改善方向应是“重用候选检索工作，再按最终问题选择”，而不是放宽到复用任何相似问题的旧答案。见[原实验](VOICE_PREFETCH_GATEWAY_RESULTS_2026-10-14.md)。

[Smart Turn](https://github.com/pipecat-ai/smart-turn)处理“人是否真的说完了”，不加快 DeepSeek 本身。官方当前版本列出中文支持。我们此前离线 45 次推理中位 68.32 ms，但用的是完整语音及人为截断片段，不能代表老人自然停顿的准确率；没有上线接管话轮。下一步应先影子运行，记录它是否抢话，再决定是否缩短静音等待。

### 3.3 更完整的首句流式需要改变提交规则

当前 ECS 已有 TTS 音频流式和投机声音准备；受控重试路径仍要等整份选段结构和来源验证完成，才发布选段。`VoiceTurns` 又等待完整答案及配置检查结束，才向手机发送声音。所以当前不是“模型写出第一个完整句子，手机就立即听到”。

可行的改动方向是让首个回答单元携带完整来源、必要条件和修订信息，经本单元验证后成为已提交内容；提交后不得再用另一请求覆盖它。后续失败须保留已听内容并明确结束或恢复，不能重新播开头。涉及条件跨句、无法独立验证的回答仍等待整段。需要单独设计并验证，不能仅把 `on_point` 回调提前执行。

## 4. API 等待究竟是什么

客户端能观察到：连接/TLS、请求发完、响应头、首个思考片段、首个正文、完整有效答案。供应商内部的排队、输入计算、调度、推理和输出生成，未必分别暴露。因此“请求已经发完但没有内容”不能一概称作模型在思考。

我们此前 8 秒异常的连接与请求发送约 104—131 ms 已完成，随后长时间没有响应头。它证明问题主要在上游响应路径，不能确定是比赛网关还是模型服务内部。另一例已开始返回正文后卡住，首 token 很快也不代表稳定。见[稳定性记录](VOICE_STABILITY_RESULTS_2026-10-14.md)。

Step 某次喝茶题：请求发完 0.080 秒，思考开始 0.536 秒，正文开始 6.156 秒，来源校验结束 6.352 秒。这里大量等待发生于思考流开始之后；`low` 仍有思考。没有证据把每一毫秒都精确划归 GPU 推理。

因此，网络不能笼统估成几毫秒；移动网络、TLS、网关转发、音频缓冲都占时间。不过在这组长等待里，网络上传不是主要瓶颈。

同样模型也会受供应商负载、配额、地区/路由、输入长度、缓存命中、推理强度和输出协议影响。不要把 tokens/s 当成首句延迟，也不要把“嗯，我看看”当作有效回答。[LiveKit 的阶段计时定义](https://docs.livekit.io/reference/agents/session-traces/)同样区分话轮、识别、模型首 token、合成首块与实际播放。

后续优先级：

1. **保留当前微信基线，单独比较 3.7 Flash low。**[官方文档](https://platform.stepfun.com/docs/zh/guides/models/step-3.7-flash)支持 low/medium/high；low 不等于关闭思考。官方吞吐不能证明本项目更快。3.5 无日期版也不能仅凭别名视为不同或更快。
2. **StepAudio 3 Realtime 做另一条架构小样。**[官方实时指南](https://platform.stepfun.com/docs/zh/guides/developer/realtime)支持自定义函数调用和结果回传，可让 ECS 提供受权限约束的记忆查询；不用把整个私人库复制到供应商知识库。初始少量可用人物资料与具体往事查询分开。还须验证工具调用往返、事实先于语音检查的能力，以及打断/撤权后清理上下文；若无法保留这些要求，不作为默认路径。
3. ASR/TTS 专用模型只解决其对应阶段，不能据名字取代文字推理。Step 5 与 Think 系列不因更新、更大就默认适合抢首句。router 的路由变化会妨碍固定模型对照，应另测。

[Step Prompt 缓存](https://platform.stepfun.com/docs/zh/guides/developer/prompt-cache)支持上述 Flash 型号复用重复前缀。可保持静态提示和有效人物资料前置、问题后置，并记录 `cached_tokens`。它不省掉输出思考，也不保证始终命中；不能为了命中缓存继续发送撤权或失效资料。

## 6. 推荐推进方式

维持现有 Android 与记忆后端，按两个独立问题推进：

- **当前管线完善**：先修年代/原因覆盖，再做候选预取与最终重排、按版本准备资料、首个完整回答单元提交、自然停顿判断。每项保留同题对照，不能一次混改后把收益全归给模型。
- **原生实时小样**：用同一批授权虚构资料，接 Step 自定义记忆工具。测简单事实、带条件的人物问题、真正连续追问、未知、工具失败和插话；把工具之前的客套话与真正引用记忆后的首声分别计时。

框架迁移本身不是本轮优先事项。LiveKit/Pipecat 可提供话轮、取消、播放和观测的参考实现，当前项目尚未用它们替换生产语音管线；Smart Turn 只做过隔离实验。Mem0/Letta 也尚未接入，不能描述成项目已经使用。

两秒是短问题的工程目标，不是现有承诺。建议先把已知事实、人物条件模拟、跨多段往事比较分别报告；同时报告 P50、P95、失败率、事实/条件遗漏及插话停声。至少保留同题多轮、慢速讲话、权限变化和完整原速录像；提前反馈不抵扣有效回答等待。
