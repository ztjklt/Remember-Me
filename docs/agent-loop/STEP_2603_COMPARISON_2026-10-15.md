# Step 3.5 Flash 2603 low：真实接入与速度对比

**Key 有效，指定模型可以调用；但本项目这组实测不支持用它替换当前快速语音模型。**带记忆后仍有数秒思考等待，调整重试也未达到约 2 秒目标。本轮完成候选适配与 ECS 隔离实测，未更换线上模型、APK 或数据库，未推送 GitHub。

## 做了什么

在同一 ECS 上复用当前已发布的来源问答路径，七题各五轮、两个模型交替，共 70 次逻辑请求。随后对 Step 追加相同七题各三轮、不在 3 秒重启的诊断，共 21 次。91 次均保留，没有删掉失败重跑取最好值。

统一使用冻结记忆、来源选择提示词和校验，保持当前快速路径不做第二次语义模型审阅。Step 参数为 `step-3.5-flash-2603`、`reasoning_effort=low`、`stream=true`、JSON Object、`max_tokens=2048`。微信保持线上参数。没有删减关键记忆，也没有通过压低输出上限强行截断思考。

前置探针：模型列表 HTTP 200；极短 JSON 请求 HTTP 200，0.557 秒首次正文，0.581 秒完成。这个数字不含记忆，**不能作为实际对话速度**。

## 速度与稳定性

以下时间均为 **ECS 发起文字模型调用到完成来源校验的等待**，不含 ASR、TTS、手机播放。中位数和 P95 只计算返回成功的请求，超时另外列出，不能忽略后一列来判断稳定性。P95 用 nearest-rank，小样本不代表服务承诺。

| 配置 | 返回结果 | 成功中位数 | 成功 P95 | 未返回 | 2秒内完成 |
|---|---:|---:|---:|---|---:|
| 微信 DeepSeek，原有3秒重试／8秒总期限 | 34/35 | 1.335秒 | 4.676秒 | 1次超时 | 30/35 |
| Step low，同样3秒重试／8秒总期限 | 18/35 | 5.823秒 | 7.350秒 | 17次超时 | 3/35 |
| Step low，不中途重试／12秒请求期限 | 16/21 | 5.968秒 | 9.483秒 | 4次超时、1次结构校验失败 | 0/21 |

第二组是接入当前策略的直接对照，第三组是另一时段的诊断，并非同轮成对实验。不能用成功中位数 5.823→5.968 推断取消重试一定更慢；成功题目组成也不同。能确定的是：不重启后确有更多完整输出，但依然远未稳定到 2 秒。

排除 UNKNOWN 的问题，成功中位数分别为 1.244、5.866、6.716 秒。Step 在第一组 2 秒内返回的三次全部是材料不足题。

所有正式测试未遇到 429、鉴权拒绝或 HTTP 5xx。Step 的超时多数是本地期限触发时仍在输出思考，不能称为供应商宕机。原3秒策略让 Step 35次逻辑请求产生65次尝试，其中47次被取消；它不适合直接套用到这个持续思考的模型。

不重试组的4次超时，模型请求在12秒被取消，上层既有重试逻辑又消耗约0.3秒后发现共享预算已耗尽，因此外层记录约12.32秒，没有再次发出模型请求。这也是后续若正式接入时应消除的额外等待；本轮没有把这0.3秒归给模型。

## 到底慢在哪里

不重试组，收到响应头的中位数约 **0.514秒**。以第一轮“你喜欢什么茶”为例：

| 从请求发起累计 | 实测事件 |
|---:|---|
| 0.080秒 | 请求已发送 |
| 0.536秒 | 开始收到思考内容 |
| 6.156秒 | 开始收到正式正文 |
| 6.318秒 | 收到完整来源选择点 |
| 6.352秒 | 来源校验结束，文字回答可用 |

这一例的大部分等待位于思考开始与正式正文之间，约5.62秒。网络传输和最后 JSON 收尾不是主要部分。这里没有调用 TTS，不能把等待归给声音合成。

low 是降低推理量，不是没有思考。本次确实收到 reasoning 流；供应商 usage 同时报告 reasoning_tokens=0，所以报告保留该计量差异，使用事件时间判定等待，不据此宣称零思考。思考正文没有进入产品答案或诊断报告。

## 关键记忆是否保留

由开发助手逐条对照原文复核，**不是独立真人盲评**。规则见 [测试口径](STEP_2603_TEST_PROTOCOL_2026-10-15.md)，91条逐题结果与完整回答见 [记录索引](evaluations/step-2603-20261015/README.md) 和 [结构化结果](evaluations/step-2603-20261015/reviewed-results.json)。

| 组别 | 合格 | 部分满足 | 未返回 |
|---|---:|---:|---:|
| 微信五轮 | 27 | 7 | 1 |
| Step同策略五轮 | 18 | 0 | 17 |
| Step不重试三轮 | 16 | 0 | 5 |

Step 完整返回的这些答案保留了淡茶偏好、个人口味条件、1987纠正和未知边界。但难题经常超时，**不能用“返回的答案全部合格”宣称它整体更准**。

具体差别：

- 微信5次旧杯子题都只说杯子的来源或“没急着扔”，没有完整回答保留原因，记为部分满足。
- Step不重试组仅有1次旧杯子题返回，找到了“看到杯子想起收车后站房喝水、一天忙完”的内容，原因更完整；另2次超过期限，不能算答对。
- 微信2次公交故事混列“已找到工作证”和旧的“还没找到”，时序不清，记为部分满足，不夸大成凭空捏造年份。
- “为什么旧记录写1986”本来就在问过去，按先后引用旧状态和纠正是合理的，未机械判错。
- 部分回答重复引用同义材料，事实合格不等于表达精炼。
- Step有1次年份题 HTTP 200、正常结束，但来源选择结构不符合协议，被拦截。日志保留 `Source selection schema invalid`，未保留该次原始选择对象，无法再定位具体字段；不将其判作年份事实错误，也不冒充正确 UNKNOWN。

源材料中仍存在“她/它”等 ASR 指代瑕疵；精确引用保留了它，模型替换不能等同于源稿已修复。

## 接入与交付状态

- 新增独立 `StepVoiceChat`：固定官方端点与模型，分离思考/正文，检查完成状态、来源、取消、共享期限与限流冷却。只接语音来源选择实验，没有将它包装成已完成全部人物归纳或记忆提取的替换。
- 新增协议探针、交替对比脚本、汇总脚本及8项适配测试；8项先在模块缺失时失败，再实现通过。相关流式、超时与来源回归合计 **63项通过**。
- Key 存在 Git 忽略的本机私有配置与 ECS 独立目录，服务器文件权限600。代码、报告、逐题资料均检查不含该 Key。
- 模型列表另列有 Step 3.7 Flash、ASR、TTS和实时音频系列；本轮只对所选2603模型做了真实推理验收，不能据列表断言其他接口均可用或更快。
- ECS仍运行 `/opt/remember-me/releases/paired-voice-stability2-20261014`，四个服务均 active。Step实验代码在 `/var/lib/remember-me/step-2603-20261015/`，没有切换服务或重新发 APK。

本机原始验收记录在 `services/backend/var/step-2603-20261015/`，含 probe、paired、no-restart、manifest及逐答案判据；其中私有环境文件不交付。公开可读的评测快照只包含虚构问题、回答与计时，不含配置凭据。

## 结论与下一步

本轮不建议将 Step 2603 low 设为快速语音默认模型。它可以留作候选，个别原因解释更完整，但目前的等待和未返回比例不足以满足连续聊天目标。

下一步应继续处理现有快速路径的长尾、遗漏原因与首声链路；若比较其他 API，沿用相同材料和完整性标准，优先看正式正文和可播放首句的时间，不用思考首 token 或极短问候的速度做替代。

本轮没有 Step Android 通话/打断录像，也不把旧微信模型视频改标成 Step 演示。新候选先达到文字环节的速度与稳定性门槛，再接手机测“停止讲话到听到回答”。冻结 follow 样本的 dialogue_context 为空，本题自己包含“茶”；本次也不能代替真正连续追问验收。
