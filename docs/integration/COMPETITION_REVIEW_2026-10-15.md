## 2. 真正能打动人的核心

**“留下一个人具体怎么生活、为什么这样选择，以及后来怎么改变；亲友既能听原音，也能带着这些依据继续交流。”**

建议用一条变化链证明，而不是罗列技术名词：

1. 一次讲述形成故事和记忆，能从花瓣回到原音。
2. Twin 对旧杯子的回答有依据。
3. 本人补充“留作纪念，不是每天喝茶”，确认修订后再问，答案保留这一否定条件。
4. 新材料单独分享给亲友；亲友也能问到新的说法，撤权后不再读到。

人物理解进一步体现“节俭但有例外”“工作方法在什么情境成立”。这才是数字孪生的产品价值；目前只实现其中一部分，不能宣传成已完整复制人格。声纹用于辨认资料来源，语音让交流省力，两者都服务于这条主线。

## 4. 已确认的整合阻断

1. **缺最新 iOS 源码。** 文档出现 `RMDesignTokens.swift`、`ForgetMeNotFlower.swift`、`Shared/RecordingActivityPresentation.swift`、LiveKit 与声纹页面，但该分支 `apps/ios` 没有这些文件或实现。不能复现构建，也不能准确定位用户所述 UI/声纹 bug。
2. **相同 URL 不等于兼容。** 两端 `/subjects/{id}/twin/answers` 的字段不同，双方 `extra='forbid'`。本次分别使用真实 Pydantic 类型验证对方 payload，都得到 `extra_forbidden`；有效登录后的请求也无法按原契约正常解析，不能仅替换地址。
3. **通话协议不同。** ECS 返回 `session_id + websocket_path`；iOS 后端返回 `call_id + livekit_url + token`。认证、取消、媒体传输和历史状态均需适配。
4. **数据库分叉。** 共同迁移止于 `0016_share_invitations`；之后 Android 走 `0017_companion…0021_twin_review_summary`，iOS 走 `0017_evidence_chunks…0024_voiceprint_entrust`。文件前缀同为 0017 不等于 revision ID 冲突，但合并后会出现两条迁移分支；不能重编号、伪造 stamp 或拿一份库覆盖另一份。
5. **整分支合并有 19 个冲突文件。** `git merge-tree` 仅预演，没有修改工作树/索引/部署。冲突包括 `api/twin.py`、`worker.py`、`access.py`、AI 提示编排、配置、依赖及迁移环境。消掉文本冲突不等于语义兼容。
6. **旧文档与当前状态混杂。** 根 README、Contract 的 v0.4、PRD 的早期“供应商未定”、iOS `ENVIRONMENT.json` 的旧迁移/安装版本都是历史快照；本目录固定版本表和代码优先。API 0.7/0.12、schema 0.4/0.12、App 版本是不同对象。

完整静态清单见 [platform-scan.json](evidence/2026-10-15/platform-scan.json)。它记录 81 个两侧同名路由声明、35 个仅 Android 侧声明、67 个仅 iOS 后端侧声明；**数量不代表兼容性或测试通过数**，也不是线上逐接口调用结果。

## 5. Android 目前真正的风险

- 本轮已发布连续语音：原路线三轮为 7.454 / 2.651 / 6.408 秒，Step 复测为 5.158 / 3.895 / 3.994 秒；数字信号测得插话约 325/324ms。没有稳定两秒，不能把首 token 或“嗯”当有效回答。
- 同题亲友人物模拟曾被独立审阅拒绝；下一次完成约 49 秒，但把“偏好淡茶”推断成“浓茶喝不惯”，仍需人工复核。因没保留首次原始草稿，不能直接认定审阅误杀或判对。
- 宽泛公交问题可能带出旧的“年份尚待核实”措辞；具体年份纠正通过不等于所有提问都清除了旧含义。
- 共用模型容量有限，后台人物任务可能挤占提取/回答；失败后原音保留，但排队与重试体验仍需改善。
- 新增资料不会自动分享，人物理解全部依据不全可见时亲友会少看到内容；这是需要解释的权限差异，不应为让两端数量一致而放宽。
- 最新组合版没有实体手机麦克风、扬声器回声、蓝牙耳机和录音豆验收。已有原速视频是预录 PCM 注入后经过真实云端与 AudioTrack，不是现场真人扬声器录音。

这些是已知证据，不等于用户提到的那个 Android 问题已经定位。没有复现步骤的故障保持“待复现”。

## 6. 声纹问题如何排查

已知代码把“聊天回答”和“本人声音自动入库”分开。没有匹配到本人时可以继续回答，资料保持未验证/第三方/待核对。测试覆盖了这一行为，但不能排除最新 iOS UI 没正确显示状态。

按以下顺序记录，不先猜是模型智力问题：

| 观察到的现象 | 应看什么 | 不能据此推出什么 |
|---|---|---|
| 点开始就失败 | App 版本/服务器、capabilities.policy、VOICE/CLOUD_TWIN、LiveKit 票据与收音就绪 | 不能直接归咎声纹算法 |
| 能聊天但没记住自己 | `enroll_owner_voice` 是否明确开启、识别许可、模型文件/校验值、清晰自我介绍、后台 utterance 状态 | 登记用的第一句本身不算后续独立匹配成功 |
| 很短一句认不出 | 16k 单声道 PCM、有效音量、至少约 1.5 秒编码输入、分段时间是否可靠 | 设备 ID/说出姓名不能证明本人 |
| 换了人仍显示旧名字 | Subject/会话/turn 归属、近似候选差值、旧 UI 迟到响应 | 不应先降低阈值硬让它成功 |
| 多人混到本人记忆 | 分段、重叠标记、本人匹配区间和 Evidence span | 单段全音频相似不等于每句话都由本人说 |
| 新内容一直不出现 | CloudBase tick、utterance/job 状态、播放完成条件、模板与许可是否撤回 | 不能因为回答已出就认为归纳已完成 |

当前匹配实现默认相似度门槛 0.70、前两候选差值至少 0.08；这是配置在代码中的决策阈值，不是准确率保证。模型缺失、太短、未知、重叠等应降级，不能伪造识别成功。队友文档中有一次声纹版本字符串超过数据库长度的失败，已记录修复；**不能未经新日志就把这次用户说的 bug 等同于那次旧问题**。

## 7. 明天合理的整合顺序

建议先维持两个已可用环境展示，另开集成分支分块验证。这不是放弃统一，而是避免比赛前把唯一工作版本一起换坏。

| 优先级 | 工作包与产物 | 完成判据 |
|---|---|---|
| P0 | iOS 补交真实客户端、依赖锁、版本、UI 截图与 bug 最短复现 | 新机器可从指定 SHA 构建同版；缺 SDK 二进制时明确获取方式 |
| P0 | 冻结 Android 0.12.1 与 iOS 当前可用版本，各自演示脚本 | 用相应账号跑故事→原音→问答；记录真实失败与等待 |
| P1 | 统一客户端能力发现和 Twin 适配边界 | 旧两端 payload 仍可用；新增能力按协商显示；不能仅捕获 422 后偷偷换模式 |
| P1 | 移植 ASR 自动校对到 iOS 后端/核对页 | 机器稿不覆盖，修改记录可读，明确确认后提取；自然采集路线另定策略 |
| P1 | 将声纹作为可选独立模块带到集成环境 | 不识别仍能录音/聊天；他人不入本人资料；撤模板和许可能失效依赖 |
| P1 | 对齐人物理解、亲友视角与更新语义 | 一次新增→条件更新→同题/改写题变化；本人/第三方/AI 的来源不混 |
| P2 | 选择最终语音传输或长期保留双适配 | 同问题多轮测有效首音、P50/P95、打断与错误率；不凭一次快结果决定 |
| P2 | 合并迁移和数据导入方案、再统一服务 | 两套数据库副本均可升级/恢复；旧授权和原音校验一致，再进行受控发布 |

可以分为“客户端/UI、记忆与模型、语音/声纹/硬件、服务与验收”四份任务，但这里不替队伍指定人员。每份都要有端到端任务与证据，而不只是改了多少文件。
