## 原来的 9.6 秒如何产生

之前喝茶时间追问误选了“喜欢淡茶”的来源。核验否定原候选、改为 UNKNOWN，随后对新答案再次核验。原记录的两段模型核验为 5.440 + 2.037 秒，首播 9.603 秒，有声起点 10.163 秒，见 `voice-reviewed-latency-20261017.md`。

修改了来源或实质回答之后，复核仍有必要。本轮避免无效返工，没有把“已经查过原稿”视为修改稿自动通过：

- `twin-quotes-v19-time-followup`：时间候选不再将“淡一点”误作时间；一般、平时、那等跟进词不再压过实际活动词。候选排序只提供提案，完整授权材料仍进入语义审阅。
- 模型慢请求保留原请求，2 秒后最多增加一个完全相同的备用请求，先完成的完整 JSON 进入原有校验，另一个取消并收尾。否定 verdict 同样先到先用，不重复请求以寻求通过。每次模型调用总截止时间仍为 8 秒。此配置可能增加慢请求的 API 消耗，不能消除所有服务商尾延迟。
- 语音 UNKNOWN 使用同一条最终措辞，修复后端将预合成内容替换成旧文案、又做一次 TTS 的问题。最终 21 轮的预备语音与最终答案匹配；仍须核验后才放行播放。
- 单要点核验不再生成不可能存在的跨要点依赖。多要点仅在完整索引集、每点均显式 supported 且无错误码时，才将漏填的依赖按全组互相依赖保守补齐；混合否定/不确定结果缺少依赖仍失败。事实、理由、覆盖范围和 verdict 不填默认值。测试覆盖无效索引、自依赖和负面结果。
- `natural-dialogue-v3`：直接接话、保留关键条件与未知，不每轮复述问题、列点或追加客服套话；温暖来自有依据的生活细节。没有相关确认理解时，不制造人物倾向和共同经历。

## 完整语音实调

问题 WAV 按原速进入真实 Android 通话音频入口；公共 WSS → 实际 ASR → 权限及记忆检索 → DeepSeek → 独立核验 → 小米 TTS → AudioTrack。问题和答案没有用文字注入。输入绕过模拟器系统麦克风，没有 vivo USB、蓝牙录音豆或物理声学回录。

“首播”是输入 PCM 结束到 AudioTrack 起点；“有声”从输入最后有声片段到输出第一段有声片段，以 10ms PCM 窗口、RMS > 200 测量，更接近听感，但仍是数字信号测量。TTS 与核验并行，不能把 TTS 用时重复累加。表中样本不是长期 P95 或真机时延保证。

## 失败样本与质量检查

开发期间的六轮旧资料批次有 1 次模型超时，随后五轮能继续；另一个六轮批次在模拟器音频驱动异常时首播 5.29–7.63s，重启模拟器后才进行上述最终回归，没有用服务端模型时间替代较慢的 App 实测值。

两个中间 Persona 批次各有 1/3 轮因核验结构缺字段失败，成功轮次也有 12.068s 慢样本。这些失败未播放预合成但尚未核验的答案。单点/全支持组结构修复后最后三轮均完成。更早的首问超时停止批次和模型层固定材料对照也保留在本地，没有只记录最快结果。

生产候选 Linux 隔离数据库测试：AI 全集 **561 passed**（10.159s），Backend 语音、会话、检索、权限与 Persona 相关测试 **110 passed**（48.573s）。XML 原始记录见本地 `payload-v7/`。录像渲染另有完整轮数、原录屏覆盖播放结束检查，防止把残缺会话呈现成完整演示；最终成片已完成实际渲染及抽帧检查。
