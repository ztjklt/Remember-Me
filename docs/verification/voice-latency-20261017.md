# DeepSeek + ECS + 小米语音延迟复盘

日期：2026-10-17。沿用既有模型、服务器、账号与语音供应商。对应用户要求：查清 49 秒等待，保留回答质量，实际测完整语音链路。

## 原因与修改

1. **49 秒样本卡在核验。** 前一轮固定虚构材料评测日志中，生成 1.686 秒，核验首次等待 45.040 秒超时，再次核验 2.125 秒，总计 48.854 秒。这是直接调用 Persona 的生成和核验时间，未包含 ASR/TTS，不能当作手机全链路耗时。原脚本绕过正式语音的 8 秒单阶段预算；现默认使用正式语音配置，`--transport direct` 才会显式走旧直调方式。
2. **实际通话反复重建记忆向量。** 检索写入向量后只 flush；下一次新鲜授权检查主动 rollback，导致未提交的派生索引丢失，每次提问重算整份档案。现先提交有内容哈希与模型版本的派生向量缓存，再重新检查当前权限、来源和版本；没有缓存回答、删减来源或放宽授权。
3. **正式 reviewed 路径没有使用原有的恢复配置。** 旧 3 秒恢复仅作用于另一条 streamed 路径。现生成和核验均采用串行恢复：首次 3 秒未完成就关闭请求，再以相同完整载荷重试一次。两个请求共享原有 8 秒阶段预算；鉴权失败、限流不盲目重试；外层不再叠加重试。
4. **恢复策略沿用旧方案已验证的串行方式。** 新增独立 `AI_VOICE_JSON_RETRY_AFTER_SECONDS`，未设置时继承旧配置；最终 ECS 配置为 3 秒。中间尝试并发备用及 1.5 秒触发，实测没有稳定改善，已撤回。没有换模型、减少材料或跳过审阅。
5. **保留语音预合成的隔离。** 小米 TTS 可在核验期间准备音频，但只有最终核验通过且文字完全匹配才允许播出；核验改稿时旧音频被丢弃。
6. **补上实测发现的指代问题。** 中间版本曾把“这种活动是哪一年”套成无关的开车年份。生成和审阅现在共享 `voice-reference-v1`：检索结果不能反过来定义用户没说清的对象；明确的历史前指仍可理解追问。这个样本需以最终实测回答评定，不能仅用单元测试证明语义正确。
7. **补充 Persona 核验字段提示。** 串行版本的普通情境样本曾因模型把 `mode` 从草稿复制到审阅结果而被严格解析拒绝（3.86 秒，不能计为成功回复）。新增 `voice-review-shape-v1` 明确输入与输出字段；没有放宽解析、丢弃多余字段或追加投票。复测三题均通过，普通情境保留家庭急事例外，追问仍是条件性表达，未知年份仍为未知。该提示不改变事实问答的 QuotedTwin 路径。

## 测量口径

- 同一正式签名 APK：Android 0.16.4-device-internal，versionCode 20261034；生产客户端未修改。
- APK SHA-256：`3004305716e99060147fbf1852dad70a8a745c52d74404ab73a6456c975c1851`。
- 在 Android 模拟器通过既有测试账号登录，预录问题按 20ms 节拍送入实际 App PCM 通道；公共 HTTPS/WSS、ASR、DeepSeek、独立模型审阅、小米 TTS、原生 AudioTrack 都实际运行。
- 只绕过模拟器麦克风 HAL，没有注入转写或预设模型答案。没有连接 vivo 真机；不据此验收真实麦克风、外放回声、蓝牙耳机或实体手机的听感。
- 主指标为**提问 PCM 输入结束到 AudioTrack 开始播放**，使用同一 Android 时钟，并按实际播放游标回推起点。服务器阶段使用单调时钟。输入尾部静音及合成开头静音另在演示 `timing.json` 标明；不是物理扬声器声学测量。

- 真实模型输出有波动，所有失败和中间版本记录保留；小样本不代表长期 P95 或所有请求上限。

## 最终实测结果

**结论：修复了主要性能回退，尚未达到稳定 3～5 秒的完整语音回复。** 最终串行配置在两次完整 App 测试中，五轮均收到真实音频并由 AudioTrack 播放；等待为 **10.619 / 8.303 / 10.827 / 6.053 / 9.871 秒**。不能只选择最快的 6.053 秒代表全部请求。基线相同 APK 的前两轮为 19.362 / 18.930 秒，第三轮失败；这只支持同题小样本的改善，不支持稳定性或 P95 承诺。

完整链路的时间单位为秒，顺序为提问输入结束 → ASR 定稿 → 记忆检索 → DeepSeek 生成 → 独立语义核验 → 播放。TTS 提前准备与核验重叠，所以不能再把 TTS 列加进总时间。

| 轮次 | ASR 定稿 | 检索 | 生成 | 核验 | 最终播出文字的 TTS 首 PCM | 输入结束至开始播放 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 常规对话 1：茶口味 | 0.967 | 0.949 | 2.249 | 5.459 | 0.521 | **10.619** |
| 常规对话 2：追问喝茶时间 | 0.700 | 1.007 | 4.095 | 1.365 | 0.345 | **8.303** |
| 常规对话 3：未说明的活动年份 | 0.936 | 1.090 | 2.114 | 2.356 + 2.369 | 0.765 | **10.827** |
| 插话测试 1：茶口味 | 0.722 | 0.986 | 1.249 | 2.207 | 0.703 | **6.053** |
| 插话测试 2：追问喝茶时间 | 0.763 | 1.234 | 1.667 | 5.412 | 0.512 | **9.871** |

- 常规第 1 轮核验、常规第 2 轮生成、插话第 2 轮核验触发串行恢复；它们的阶段时间已经包含首次等待和重试，没有另加或隐藏。
- 常规第 3 轮初稿仍选到不相关经历，独立核验拦截并修正为未知，再次核验后才播出。旧初稿预合成首 PCM 为 0.563 秒，已丢弃；表格计的是最终未知回答的 0.765 秒。不能把这条算作一次性生成质量通过。
- 除表内模型阶段外，后端权限复查、来源/结构校验及调度分别约 0.44 / 0.33 / 0.64 / 0.34 / 0.33 秒；答案就绪到手机开始播放分别 0.553 / 0.806 / 1.318 / 0.550 / 0.462 秒（含最终音频等待和交付）。这些项目与模型内部毫秒级开销、四舍五入会有小差异。
- 另按输入最后有声片段到首个有声输出测量，五轮为 **11.159 / 8.893 / 11.177 / 6.573 / 10.451 秒**。此口径剔除了输入尾静音，包含合成起始静音，更接近听感；仍是数字 PCM 测量，不是物理声学回录。
- 插话输入开始至 AudioTrack 停止旧回答 **265ms**；之后新一轮回答完成。退后台自动暂停、返回保持暂停并显示“继续”、点击结束释放通话均通过。
- 当前完整 App 用的是同一联调账号的事实问答 reviewed 路径。该账号缺少 Persona 所需的已确认人物理解/表达材料，未绕过准入门槛；下面的 Persona 数据是独立固定虚构材料测试，不能冒充手机 Persona 端到端验收。

| 样本 | 生成 | 核验 | 总耗时 | 结果 |
| --- | ---: | ---: | ---: | --- |
| 普通临时安排 | 1.925 | 2.443 | **4.62** | 保留“平常先问清；家庭急事例外” |
| 家庭急事追问 | 1.346 | 2.439 | **3.81** | 条件性回答，没有生成新承诺 |

仍需改善的是供应商响应长尾和模型初稿质量导致的额外核验。现有证据不支持“已稳定恢复旧版 3 秒”，也不支持“小米 TTS 是主要瓶颈”。保留独立核验的当前架构至少有两次模型请求的依赖关系，不能通过在核验完成前播出、切换快速模式或截掉必要条件来制造低延迟数字。
