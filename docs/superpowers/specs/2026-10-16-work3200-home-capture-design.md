# 录音豆首页录音闭环：复盘与拟议设计

日期：2026-10-16。基线：`3c81943`，Android `0.13.0-device-internal`。
状态：用户已确认，授权按方案直接实施、后续常规步骤自主推进；本文不表示功能已经实现或实物已验收。

## 用户要完成的事情

用户在“今天”首页以录音豆作为主要录音来源。按录音豆按钮开始、暂停或结束时，首页反映设备真实状态、时长和重点标记；结束后在同一首页继续接收文件、查看进度、试听、转写、核对并整理记忆。切换 App 内页面不应断开连接。保留用户主动选择的手机录音方式。

成功标准不是显示“已连接”，而是同一段真实设备录音从开始到整理都有可解释的状态、下一步和可恢复的失败处理。

## 已确认的根因与实物证据

1. 用户截图可见 `soundcore Work`、电量 90%、固件 04.92，证明已发生连接和设备信息读取。截图仍是“手机已保存：0 段”，没有下载或试听成功证据。
2. 第三张截图 `binding/3` 对应 SDK 1.3.02 的 `BINDING_CONFIRM_TIMEOUT = 3`。这表示等待设备实体确认超时，不能把前面的传输连接视为绑定完成。
3. `Work3200Screen.kt` 在 Composable 中创建控制器；`onDispose` 调用 `controller.close()`，`ON_STOP` 调用 `disconnect()`。因此从“我的”回到首页就主动关闭连接，系统授权/导出页面也可能影响当前会话。
4. `TodayStoryScreen.kt` 的“讲一段”进入 `StoryRecordingFlow`，该流程申请 `RECORD_AUDIO` 并调用 `model.start()`；`NativeWorkbenchModel.start()` 调用手机 `audio.start()`。首页没有录音豆输入来源。
5. `SoundcoreCallbacks.java` 中录音状态和时长方法为空实现；实际 `Soundcore1302Bridge` 未覆写这两个方法，`HardwareEvents` 也没有对应事件。因此实体按钮不会更新首页。
6. SDK 文件标记虽转发到 `HardwareEvents.markers`，控制器实现仍为空；传输状态带的标记列表被丢弃。
7. 下载文件仅进入独立 hardware journal，没有进入 `NativeWorkbenchModel` 的本机录音列表和上传流程。后端已经支持 `WORK_3200` 来源，但客户端没有把两条流程连接起来。
8. 当前 `busy` 单字符串把绑定、录音、同步和播放混在一起；所有非信息类错误都直接断开连接，页面没有区分连接失败、绑定失败、文件操作失败。

根因证据来源是本地源代码、用户截图、交接包内 `sources/sdk-guide.html` 和私有 SDK `classes.jar` 的公开签名/常量。没有把模拟器结果当作实物结果。

## 厂商能力与边界

| 用户操作/反馈 | 已核实能力 | 接入方式 |
| --- | --- | --- |
| 实体按钮开始/结束录音 | `onAudioRecordStatusChanged`：停止 0、录音 1、暂停 2，携带 fileID 和时长 | 转为统一设备状态事件，更新首页 |
| 录音秒数 | `onAudioRecordDuration(durationMs)` | 以设备毫秒为基准；只在有效录音状态内平滑显示计时 |
| 连接时已在录音 | 指南定义 `DeviceInfo.recording` 为 0/1，`recodingOriginalTime` 为按下录音键的时间戳，未录音为 0；SDK 支持先录音后连接 | 该时间戳不能直接当作已录毫秒；优先以状态回调和文件 ID 恢复，身份未知时不猜测最近文件 |
| 录完接收文件 | 文件列表、蓝牙传输、文件落盘回调 | 按录音 fileID 匹配，等待文件可下载，再串行下载 |
| 下载进度 | `onTransferFileProgress(total,current,...)` | 已接收/总量百分比；完成后单独校验 |
| 文件重点 | `onDecodeFileMarkers` 的毫秒偏移、传输状态标记列表 | 按 fileID 保存、去重、显示为可点击时间点 |
| 实时重点 | 实时片段 `isMark` 和序号 | 仅在实际收到 SDK 标记事件时显示设备重点；不能凭手机按钮假装设备写入成功 |
| 手机补充重点 | 可由 App 在当前已知录音时间轴写本地标记 | 明确显示“手机添加”，与设备重点保留来源区别 |
| App 远程开始/结束录音 | 当前公开 SDK 方法没有完整支持 | 主流程由实体按钮开始/结束，不把 resumeRecord 当成开始录音 |
| 暂停/继续 | `pauseRecord` / `resumeRecord` 仅对已开始的录音适用 | 若展示则仅在对应有效录音状态启用，等待设备回调确认 |

SDK 指南的部分示例签名早于 1.3.02；以随包 AAR 的实际签名校正适配器，不复制过期示例。

## 可选实现路线

1. 仅把旧连接页放到首页：改动少，但仍缺统一状态、自动收尾和转写入口，不满足用户目标。
2. **推荐：设备会话独立于页面，首页统一承接录音生命周期。** 状态实时反映，结束后取得完整文件，接入现有转写/核对。对设备传输协议的依赖可控。
3. 全量边录边传、实时解码和实时转写：需要额外处理包序、重传、并行文件、网络连续性。用户当前要求的实时状态反馈不要求把这整条实时转写链路一起交付。

采用路线 2。对 SDK 实时标记能力做有界接入/验证；完整录音以结束后校验过的文件为准。

## 首页具体流程

首页保持当前视觉和导航，新增主要录音卡片，不要求用户先进入“我的”。

顶部来源选择：`录音豆` / `手机`。本设备联调版首次默认录音豆，此后保存用户选择；设备断开时不静默改用手机麦克风。

| 状态 | 首页显示 | 可执行动作 |
| --- | --- | --- |
| 未连接 | 录音来源：录音豆；连接后按设备按钮开始 | 连接录音豆、主动切换手机录音 |
| 等待绑定 | 已建立连接，等待充电盒确认；具体操作和超时提示 | 重试绑定、取消绑定/断开 |
| 待命 | 设备名、电量、已就绪；按录音豆按钮开始 | 查看设备录音、设备管理 |
| 正在录音 | 明确“录音豆正在录音”、`mm:ss`、重点数 | 标记重点；按设备按钮结束的提示 |
| 暂停 | 已暂停，计时冻结 | 设备继续或支持的恢复操作 |
| 录音结束 | “录音已结束，正在取得本段文件”与本段时长 | 文件尚未就绪时显示等待，不误报已保存 |
| 同步到手机 | 同步本段：实际百分比 | 中断后重试本段，不要求重新绑定 |
| 校验/转换 | 正在校验/转换，阶段明确 | 格式异常时保留原件、导出诊断、重试 |
| 已保存 | 时间、时长、来源、重点、手机本机保存位置入口 | 试听、从重点播放、转成文字、查看全部录音 |
| 上传 | 上传本段：实际发送比例；等待服务器确认单独显示 | 网络错误后保留原文件和幂等键，可重试 |
| 云端处理中 | 转写中/等待核对/整理中等真实状态 | 在首页继续核对、整理或查看结果 |
| 完成 | 本段对应的转写/记忆入口 | 查看、再录一段 |

首页先完整呈现最近一段任务，其余已保存录音在首页展开列表及“档案 → 我的录音”中可找回。核对界面可以在首页打开全屏编辑，但关闭后回到原录音卡片，不跳回设备设置。

手机来源继续使用现有手机录音流程；麦克风权限只由明确选择手机录音的操作触发。

## 连接与绑定生命周期

- 唯一设备会话由账号/人物作用域的管理器持有，页面只订阅 `StateFlow`；任何 Tab 离开都不关闭设备。
- 连接由用户在前台主动发起；使用 Android `connectedDevice` 前台服务维持正在使用的设备会话，通知显示设备连接/录音/同步状态并提供返回首页或断开动作。不要把它声明成手机麦克风服务。
- 锁屏和短暂切到其他 App 不主动断开；强行结束 App/系统杀进程后不承诺永久在线，重新进入时明确显示恢复/重连，不能保留假的“正在录音”。
- 主动断开、退出账号、切换人物或更换服务器才结束当前作用域的设备会话；晚到回调不能写入新作用域。
- 记录扫描返回的绑定状态，但“设备已被绑定”不等同于“当前账号已获可用权限”。优先依据当前会话确认及文件访问结果，不反复要求已完成的绑定，也不自动解绑别人的设备。
- `binding/3` 显示“等待充电盒按键确认超时”，提供明确重试。官方指南建议绑定异常后重连，因此保留这一恢复路径；文件列表/下载失败不一律销毁已授权会话。
- 连接断开期间，设备可能继续独立录音；页面显示“连接断开，设备录音状态待确认”，不能把断开直接显示成录音结束。

Android 依据：https://developer.android.com/develop/connectivity/bluetooth/ble/background 。需进一步核对前台服务声明和权限，并实测 vivo 后台行为。

## 同步、存储、转写与重点

- 用户在首页主动连接设备后，默认将本会话观察到结束的那一段同步到手机；历史录音仍由用户选择，不批量自动导入。
- 只按匹配的设备 key + fileID 自动处理；结束回调可重复、列表可能稍后更新，使用串行任务队列和有界重试。缺失 fileID 时让用户选择，不猜最新项。
- 文件传输、解码、上传、转写分别有状态。不得以 `100%` 的蓝牙传输显示“记忆已生成”；只有真实文件校验/服务端确认才进入下一阶段。
- 原始设备文件和标准音频分开保存；沿用 hardware journal 的来源、哈希、幂等键和账号/人物隔离。格式不符时原件仍可导出。
- 复核现有解码器的 8 MiB 原文件、100 MiB PCM 和 120 秒执行上限；这些是保护性实现限制，不是设备录音时长承诺。较长录音若超出当前处理能力，应在首页明确给出文件已保存/尚未转换及导出入口，不能卡在无限进度或声称整段完成。
- 标准音频通过 `WORK_3200` 来源进入现有 `LocalCapture`/上传/核对流程；持久化元数据不能只对 `IMPORT` 生效，否则重启后会丢失入口。上传重试与 journal 共用稳定幂等身份，并回写同一 episode。
- 录音结束后自动同步只发生在设备和手机之间。云端上传延续现有用户确认；首页“转成文字”旁说明上传用途。没有确认不上传，不自动确认转写，不自动删除设备文件。
- 重点按毫秒偏移持久化，并区分设备和手机添加；点击从该时间点播放。实时设备重点只有收到可信回调才出现，离线重点在文件同步后补全。
- 当前服务端没有真实细粒度转写百分比，`read_status` 明确省略 `progress`。本轮显示下载/上传/可计量转换的真实百分比，云端阶段显示状态和等待时间，不补造递增数字。
- 现有服务端 `WORK_3200` 和 arbitrary capture metadata 可复用；不为首页接入另建服务，不改变已冻结的必填字段/枚举。新增标记元数据只做可选兼容数据，不宣称 AI 已按重点处理。

## 实施涉及的位置

- `hardware/HardwareTransport.kt`、`Soundcore1302Bridge.java`：设备状态、时长、绑定信息、标记、传输事件。
- 新的可单元测试设备录音状态机：处理乱序/重复事件、生命周期、进度和本段匹配。
- `Work3200Controller.kt` 与设备会话管理/前台服务：不依赖页面，操作分离，可恢复错误，串行下载。
- `Work3200ImportJournal.kt`、`DeviceOpusDecoder.kt`：标记保存、准备文件复用、可计量转换、失败原件保留。
- `NativeWorkbenchModel.kt`、`CaptureSubmission.kt`、`BackendClient.kt`：设备导入与现有上传衔接、持久化和上传进度。
- `TodayStoryScreen.kt`、`NativeWorkbenchScreen.kt`、`Work3200Screen.kt`：首页来源选择、设备状态卡、最近录音卡、核对入口及原设备管理页复用。
- `MainActivity.kt`、`AndroidManifest.xml`：服务和生命周期；仅在需要的层级释放资源。

## 验证与交付标准

1. 单元验证：开始→计时→重点→结束；暂停计时；重复开始/结束；旧文件事件；断线未知状态；列表延迟；跨账号回调；重复下载/上传；标记单位/去重；0 总量进度；转换失败；已上传文件可再次试听。
2. UI/运行验证：首页能连接；切“我的/档案/今天”会话保持；录音豆路径不触发手机麦克风授权；手机模式仍能录音；错误页明确 binding/3；前台服务启动、通知、退出账号释放；首页接入已保存录音、上传和核对。
3. 联网验证：用明确标注的测试材料检查 `WORK_3200` 上传、机器转写待核对、本人确认后整理、返回同一任务；不能把测试材料当作实物音质证据。
4. 用户实物验收：vivo 手机 + 固件 04.92；实体开始后首页反应，约 30 秒计时，添加重点，切页面，实体结束，匹配本段自动下载，清楚试听，重点跳转，上传转写和核对生成对应记忆；再做一次锁屏/恢复、断开重连、重复下载。
5. 发布同签名可覆盖安装的新版 APK、安装说明、文件哈希、已跑检查与未完成项。无需用户开启 USB 调试；实物问题通过 App 导出诊断定位。

在第 4 项有证据前，交付措辞只能是“软件流程已实现/测试，待设备验收”，不能称全流程已打通。
